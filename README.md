# 文化資料登録室

公開案内ページ: https://bunka-shiryoshitsu.github.io/bunka-shiryoshitsu/

申請・管理機能: Cloudflare Worker `bunka-shiryoshitsu-checksoft-mountain-b5a9`

## 動作確認

Node.js 22 以降で、初回に `npm ci`、その後 `npm test` を実行します。テストはメモリ内の専用データだけを使い、本番の申込・登録・画像を変更しません。

検証対象は、公開画面のスクリプト、管理認証、受付停止、抽選申込、当選設定、画像提出、登録申請、審査、登録番号照会、JPGの登録・本人受取、登録取消です。資料の審査と登録書JPGの作成は管理者が行います。

## 公開

`wrangler.jsonc` の入口は `worker.js` です。既存の KV、Durable Object、管理キーを維持してください。古い `worker-dashboard9.js` を直接指定すると登録番号管理画面が外れます。

公開前にテストと `wrangler deploy --dry-run` を行い、現在の公開バージョンを記録します。公開は `wrangler deploy --keep-vars`、公開後はトップ・申込・受取・管理画面の応答を確認します。

有料プラン、新規有料サービス、追加費用のある操作は、所有者に相談するまで実行しません。秘密鍵や管理キーをリポジトリに保存しないでください。

開発用 `/_dev/` と切替検証用 `/_cutover/` は本番で404になります。古い検証ファイルを公開入口に指定しないでください。

## AP番号だけでの状況確認・受取

所有者の指定により、申請者は既存・新規ともAP番号だけで状況確認、追加提出、登録書受取を行います。AP番号を知る人はこれらを利用できるため、申込完了画面・受取画面・HPに「AP番号は他人に教えないでください」を22〜28pxの大きな文字で表示します。

受取キーの発行・照合・表示・コピー・再発行は廃止しています。既存キーの記録と旧暗号化設定は使用しません。これらは切替時に一括削除せず、運用復旧用に保持しています。新規受付に暗号化設定は不要です。

AP未入力・不正・未登録は拒否します。同じ接続元から15分以内に10回確認に失敗すると、その接続元の確認を一時制限します。制限は既存KVによる補助的なもので、厳密な同時実行制御ではありません。登録番号単独・別APの登録書・取消済み登録書の取得は引き続き拒否します。

③申請・審査には「受取画面を確認」を設けています。管理者専用プレビューは管理者ログインが必要で、追加提出・取消はできません。

# 追加提出（2026年9月実装）

- HPの「申請状況の確認・追加提出・登録書の受取り」から、AP番号で確認します。審査中は週に一度の確認を案内し、メール・相談対応は設けていません。
- 管理画面の申請詳細から、資料ごとに依頼内容と文章／画像の要否を指定します。翌日から30日間、締切日の23:59（日本時間）まで提出できます。初回の申請期限とは独立します。
- 元の申請・画像を上書きせず、追加依頼と提出履歴を既存のRegistrationIssuerのSQLiteストレージに保存します。画像はJPEG/PNG/WebP、1枚3MB、1依頼10枚まで。画像は認証後のみ取得できます。
- 期限切れは自動不承認にせず、管理者が延長または「未提出による手続終了」を選びます。追加提出一覧で提出待ち・期限切れ・提出済みを確認できます。
- 新規の当選期限は申込月の翌々月1日を含む60日間。既に保存された当選情報の期限は変更しません。
- 新しい有料サービス・バインディング・プラン変更はありません。追加ストレージも既存の無料枠を使用します。
- `npm test`で日付境界・認証・画像制限・二重送信・延長・手続終了・審査後の再提出拒否を検証します。

## 追加提出画像の削除

登録決定・登録見送り・未提出による手続終了時に、当該資料の追加提出画像を削除します。依頼文、追加文章、提出日時、画像の提出履歴は保持します。審査中・追加提出待ちの別資料の画像は削除しません。

## 管理者専用の点検画像

審査確定・未提出による手続終了の前に、申請画像と提出済みの追加画像から点検用の縮小版を管理画面で作成します。長辺1200px以内・JPEG 150KiB以内で、白背景への描画により位置情報などの付加情報を引き継ぎません。縮小保存・全画像の確認が完了しない場合は確定処理を停止し、元画像を残します。未提出・取下げ済みの追加添付は点検保存しません。

- ③申請・審査の「点検用画像・保存期限を確認」から20枚ずつ表示・拡大できます。管理キーを必須とし、URLだけでは画像を取得できません。公開ページ・申請者の受取画面には表示しません。
- 確定後180日保存し、期限到来または容量上限で自動整理します。確定前に中断された準備用コピーは24時間で整理します。申請・登録情報、番号メモ、登録書は点検画像の整理対象外です。
- ⑥設定に枚数・使用量・容量上限・削除予定・自動整理件数を表示します。上限は初期200MiB、50/100/150/200MiBで変更できます。既存SQLite Durable Objectに格納し、新しい有料サービスやバインディングは追加しません。データベース全体が800MiBを超えないよう新規保存の余地も確認します。80％から注意を表示します。
- 容量が足りない場合は保存期限の近い確定済みコピーから整理します。期限を延長したコピーも容量上限の対象です。90％以上では延長を止め、延長先は操作日から1年以内とします。
- ⑥設定の「既存の確定済み画像を縮小保存」で、導入前から残っている元画像を処理できます。その場合は保存開始から180日です。削除済み画像を復元する機能ではありません。
- 画像のチャンク・管理情報・容量計数・期限索引は同一トランザクションで保存します。保存途中の失敗・再送で容量を二重計上しません。既存アラームと日次処理で期限削除・元画像整理の失敗を再試行します。期限を過ぎた画像はアラーム実行前でも取得できません。

`tests/inspection-images.test.mjs`で管理認証、容量・サイズ制限、確定前の保存確認、保存失敗時のロールバック、再送、180日期限、延長競合、容量による整理、保存領域の余裕、確定直後の中断からの回復、追加画像の提出状態を検証します。

削除が途中で失敗した場合も、終了済み資料の追加画像は取得できません。既存のDurable Objectの永続アラームで約1分後に再試行し、大きな履歴は分割処理します。以前のバージョンで残った終了済み画像も、申請状況の表示時と既存の日次処理で整理します。対象の終了状態を確認できない場合は画像を残します。新規のバインディングやCron設定の追加はありません。

## 登録番号ごとの管理者用メモ

`/admin/registration-numbers` の自己所有品専用プール、一般申請用の生成台帳・発行済み台帳に、番号ごとのメモ欄を設けています。5000文字以内、改行可。「保存」で保存し、空欄を保存するとメモを消せます。同じ番号は台帳をまたいで同じメモを表示します。

メモの読み取り・保存は管理キーで認証します。番号・発行台帳とは別に、既存のRegistrationIssuerの永続ストレージへ `registration-number-note:<番号>` として保存し、公開照会・登録書・申請者画面には含めません。世代番号によって別画面からの古い更新を拒否し、保存失敗時や未保存の入力は画面に残します。新しいサービス・バインディング・有料プランへの変更はありません。

## 管理画面の共通操作

管理画面の上部に「1 要対応 → 2 抽選管理 → 3 申請・審査 → 4 登録・登録書 → 5 番号・メモ → 6 設定」を常時表示します。どの画面からも移動でき、選択中の画面を色と現在位置で示します。旧 `/admin-winners` は `/admin?view=lottery` に移動します。

各画面に「番号・プール一覧」の共通ボタンも設けています。「全番号・メモ」「自己所有品プール」「一般番号プール」「発行済み番号」へ直接移動でき、設定画面の予約番号プール件数の横にも一覧リンクがあります。概要の予約番号プール件数は自己所有品プールへ移動します。

番号画面内の一覧切替では、取得済みデータと未保存メモを保持して50件ずつ再表示します。直接URLは `/admin/registration-numbers?scope=all`・`scope=owner`・`scope=pool`・`scope=issued` です。直行ボタンは以前の検索語を解除して指定の一覧を表示します。一般番号プールには生成済み番号を、発行済み一覧には発行記録のある番号を表示し、生成・発行の両記録がある番号は1枚のカードにまとめます。

要対応画面では追加提出済み・期限切れ・提出待ちを絞り込み、該当するAP番号・資料番号へ直接移動します。件数は表示中の100件以内を対象とし、続きは「次の100件」で確認します。概要の件数からも対象の一覧へ移動できます。受付の開始・停止は「設定」にまとめています。

申請・登録・番号台帳のAP番号と登録番号は関連画面へのリンクです。申請内の資料は切替ボタンで選択します。検索語、絞り込み、一覧の位置、最後の資料は同じタブ内で保持します。番号・メモでは重複する番号を1枚のカードに集約し、生成・発行履歴は展開して確認します。日時は日本時間で表示します。

名称や追加依頼の未保存の文章は、このタブのsessionStorageに下書きとして保持します。③で選択した完成登録書JPGは、同じタブ専用のIndexedDB領域に画像の下書きとして24時間保持します。「文章・画像の下書きを保持して移動」で⑤番号・メモへ移動して戻った場合も復元します。保存・破棄・ログアウトで画像下書きを消去し、期限切れデータは管理画面を開く際に整理します。タブを閉じた場合やブラウザーの保存領域を消去した場合の復元は保証しません。下書きの保存先を利用できない場合は警告し、画像を失う移動を止めます。番号メモの画面移動時は保存・破棄・編集継続を選択し、保存失敗や競合があればその場に留まります。管理者認証は既存の24時間セッションを使用し、管理キーをURLや下書きに含めません。

完成登録書JPGは「① JPGを選択 → ② 赤いボタンで保存」の順で登録します。選択だけでは申請者に反映されず、未保存画像と保存済み画像を区別して表示します。成功後も画像・ファイル名を残し、別の未保存の文章は保持します。再訪問時は管理者用の受取確認APIから保存済み画像を取得します。保存中は対象資料の入力と移動を止め、通信失敗時は選択した画像を残します。`tests/admin-document-upload.test.mjs`で選択・保存・下書き復元・破棄・通信失敗・保存中の操作を検証します。

審査・取消の確認には対象のAP番号・資料番号・名称または登録番号を表示します。狭い画面では一覧を項目名付きのカードに切り替え、入力欄と操作ボタンは16px以上、主なボタンは高さ44px以上にしています。キーボードで移動し、入力欄・画像・リンクの選択位置を確認できます。

## 番号・メモの大量件数対策

番号は50件ずつ表示し、「前の50件」「次の50件」で切り替えます。検索は全件の番号・AP番号・メモを対象とし、未保存のメモもページ移動中は保持します。画面上の入力欄は最大50件だけを作成し、メモの入力・保存時に全件の表示を再計算しません。

メモは100件単位・同時に最大3通信で取得し、取得済み件数と中止ボタンを表示します。通信ごとに15秒、読み込み全体に60秒の待機上限を設け、失敗・中止後は再試行できます。保存の応答が届かない場合も入力を保持し、再試行には既存の世代番号と同一内容の再送処理を使用します。

再発防止の検証には、1万件の全件検索・重複統合・50件ずつの描画、ページ間の下書き保持・保存、読込中止・再試行・通信待機上限を含めています。画面構築の検証ライブラリは開発用で、公開Workerには含めません。

## 一覧取得の利用上限への対応

番号一覧と作業件数のためのKVキー探索は、既存のDurable Object内に1時間保持して管理画面間で共有します。`ADMIN_KEY_CACHE=true`で有効です。アプリ内で関連キーを追加・削除した際は保存済み一覧にも反映します。番号発行時の衝突確認には従来どおりKVを直接使い、古い一覧で発行可否を判断しません。管理外で変更したキーは次回の一覧再取得時に反映します。

KV listの一日上限に達した場合は、翌日00:00 UTCまで一覧探索の再試行を止めます。過去に確認できた番号一覧がある場合は、そのキーから現在の番号データを直接取得して表示・メモ編集を続けられます。未確認のプール件数は「確認待ち」とし、0件とは表示しません。作業件数も不明な場合は確認待ちを示します。画面の自動更新は5分間隔とし、上限到達時は再試行を停止します。サーバーがHTMLのエラーを返しても、利用者には日本語の再確認案内を表示します。

過去の確認記録からキー一覧のみを復元する管理者用POST `/admin/key-cache/restore` を設けています。`prefix`、`keys`、確認時刻の`at`を受け取り、すでに保存済みの索引は上書きしません。番号・メモ・画像本体を変更する操作ではありません。内部の保存APIは公開経路から到達できません。
